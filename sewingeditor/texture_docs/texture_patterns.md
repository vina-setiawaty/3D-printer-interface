# Texture Patterns

Every texture should be generated by calling a function from
`texture_functions.js`, never by re-deriving its geometry. Signatures
below were pulled directly from the current code — if they ever disagree,
trust the code and fix this file.

**Extrusion is relative (`M83`), not absolute.** Every `G1 E<value>`
this library emits is a delta — positive extrudes, negative retracts,
independent of anything printed before it — so each function's output is
a genuinely self-contained, insertable unit. See `troubleshooting.md`
§11 for the rationale and what changed.

**All line styles share one identical signature:**
`(em, xFunc, yFunc, tStart, tEnd, options)`. This uniformity is what makes
them safely interchangeable as `fill()` styles — it is a load-bearing
property, not a cosmetic one. If a new line style is ever added, it must
match this shape exactly (see `troubleshooting.md` §8 for what broke when
two functions didn't). `freeformBlobDotted` (added after the original six)
follows this same signature.

**Two kinds of entries:**
- **Line styles** — called directly with `xFunc, yFunc` parametric path
  functions. Any of these can follow a straight line, an angle, or a curve.
- **Fills** — called through `fill(em, region, style, options)`, where
  `region = {x0, y0, w, h}`. All fills EXCEPT diamond route through the
  generic `fillRegion()` mechanism.

**Before generating any multi-texture print**, call `verifyLayout()` and
confirm `ok === true` — see `global_printing_parameters.md` → Multi-Texture
Layouts. Nothing else in this library checks whether two textures overlap.

**Calibration line convention (standing, as of 2026-08-26, updated same
day)**: every test print generated from now on starts with a plain
`freeformSolid` reference line from x=120 to x=180 (shifted +60mm from
the original x=60-120 range), printed BEFORE the texture under test, not
after. First instance printed at y=200; each subsequent generated file
uses y 5mm lower than the last (195, 190, ...). Check `CHANGELOG.md` for
the most recent entry's calibration-line y before generating the next
file, to keep the sequence correct and non-overlapping. This is a
test-harness convention, not a `texture_functions.js` function — it's
built inline in each generation script, same as every other test print in
this project.

## Dots

### Blob dot — ✅ implemented, DEFAULT, ✅ v17 CONFIRMED BEST on hardware
`blobDot(em, cx, cy, {diameter = 1.6, baseZ = 0.2, buildSteps = 6, taperFactor = 0.7, extrudeSpeed = 120, dwellMs = 2000, extrusionMultiplier = 1.3, retractMm = 4.0, postRetractDwellMs = 2000, baseExtraMm = 0.3, baseDwellMs = 1000, orbitRadius = null, orbitPts = 16, orbitSpeed = 600, orbitLoops = 3, orbitDwellMs = 2000, blobClearanceMm = 0.3, liftZ = 5.0, liftSpeed = 600, liftDwellMs = 1000, topOrbitLoops = 3})`

The default dot texture. Builds a small dome by extruding WHILE rising in
Z in `buildSteps` small increments (no XY movement) — heaviest at the
bottom, tapering by `taperFactor` toward the top (0.7: the last step lays
down only 30% of the first step's rate, deliberate coasting) — rather
than extruding the whole blob in one instantaneous burst. The very first
step deposits an extra anchor blob (`baseExtraMm`) and dwells
(`baseDwellMs`) before continuing to rise. Then dwells, retracts (a
dot-specific `retractMm`, larger than the shared global default), dwells
again, loops a full circle around the dot **at the dome's own top
height, repeated `orbitLoops` times** (the original, hardware-confirmed
orbit — briefly and mistakenly removed in v15, restored in v16),
re-centers, dwells, lifts clear (`liftZ`), dwells, then **(v16)** loops
the same circle again, **`topOrbitLoops` times, at that lifted height**
— clearly higher than the dome — before traveling to the next spot.

> **(v17) CONFIRMED BEST RESULT ON REAL HARDWARE — "Yes this works
> best."** The code for the recenter, both dwells, the lift, and the
> second (lifted-height) orbit — steps 6 through 10 above — is currently
> commented out in `emitBlobDot`: the sequence now goes straight from the
> first (dome-height) orbit to the next dot's own travel move, and
> nothing else. This IS the current best-known configuration — steps 6-10
> are confirmed NOT needed, not just untested. The parameters for the
> disabled steps (`orbitDwellMs`, `blobClearanceMm`, `liftZ`,
> `liftSpeed`, `liftDwellMs`, `topOrbitLoops`) still exist on the
> function signature but currently have no effect; leave them commented
> out unless a future test specifically wants to re-isolate them. See
> `troubleshooting.md` §10 for the full isolation rationale and result.

**v8 — no stationary extrusion, anywhere**: the priming restoration
(`retractMm` + first-dot prime bonus) used to be emitted as its own
`G1 E...` line while the nozzle sat still, right before the tapered
build even started — exactly the kind of instantaneous pressure dump
the whole build-while-rising design was meant to avoid. It's now folded
into the first build step's E value instead, so the very first upward Z
movement already carries it. Extrusion and motion are never separated
anywhere in this function.

**v8/v9 — recenter after orbit**: the FIRST orbit's last point ends
`orbitRadius` away from the dot's center, not back at it. Lifting/
traveling from that off-center position wasn't ideal, so after the
orbit(s) the nozzle explicitly returns to (cx, cy) (at `z +
blobClearanceMm` since v13) before lifting. v9 swapped the order so the
dwell happens AFTER re-centering (not before, as in v8) — giving
residual melt pressure time to relax at the dot itself, rather than
dwelling off-center before the final move back to center. v15 briefly
removed this recenter step entirely (see below) — v16 restored it, since
it's needed by the first (dome-height) orbit regardless of what happens
after the lift.

**v6 removed two earlier steps** (a pre-retract drop, and a post-retract
lift→drop→lift): both squished/deformed the dot on real hardware without
clearly helping stringing, so they were dropped in favor of the orbit
below, which happens right at the dome's own height instead of relying
on vertical pressing.

**Volume model** (ties `baseZ` and `diameter` together, see
`troubleshooting.md` §10): the blob's total volume is modeled as a
cylinder filling the nozzle standoff gap, `π·r²·baseZ`, plus a
hemispherical dome bulging above the tip, `(2/3)·π·r³`. The sum is
converted to filament length via `FIL_AREA` (same conversion used for
bead E-rates elsewhere), scaled by `extrusionMultiplier`, then split
across the `buildSteps` rise steps by the taper weights. There is **no
separate height parameter** — dome height above the standoff is
~`diameter/2`, which clears the 0.4mm Relief Height Floor for any
`diameter >= 0.8mm`.

**Anti-stringing** (four combined mechanisms — see `troubleshooting.md`
§10 for the full history of what was tried, including the several
dome-height/vertical-squish mechanisms that were tried and then removed
across v1-v14, and the v15 mistake corrected in v16):
1. Extruding across the whole rise, tapering to a near-stop at the top
   (`taperFactor`), avoids the nozzle-pressure spike that a single burst
   leaves behind — now including the priming restoration too (v8), not
   just the print volume.
2. A larger dot-specific `retractMm` pulls the melt further back
   immediately after building.
3. Immediately after retract — before any lift — `orbitLoops` full
   circles (`orbitRadius`, default the dot's own radius) traced right at
   the dome's own top height, no extrusion: sweeps at the height where
   any residual string is actually attached, rather than trying to press
   it down vertically. **Confirmed on real hardware to reduce
   stringing** ("There's definitely less stringing now").
4. **(v16)** After re-centering, dwelling, and lifting to `liftZ`, the
   SAME circle is traced again — `topOrbitLoops` times — at that lifted
   height, clearly above the dome, on the theory that a trailing strand
   might sag away from the dome-top height that mechanism 3 sweeps at.
   Replaces the v10-v14 `postLiftBounces` (vertical down/up cycles) and
   the v14 second wider/lower orbit, neither of which is used anymore.

v15 briefly REMOVED mechanism 3 (the original, hardware-confirmed
dome-height orbit) by mistake while trying to implement mechanism 4 as a
replacement for `postLiftBounces` — it was misread as a request to
replace both orbit-type mechanisms, when only the bounces and the v14
second orbit were meant to be replaced. v16 restores mechanism 3 and
keeps mechanism 4 as an addition, not a replacement, of it.

### Directional blob dot — ✅ implemented, v3, ✅ hardware-confirmed working
`directionalBlobDot(em, cx, cy, {diameter = 2.0, azimuthDeg = 0, baseZ = 0.2, buildSteps = 6, taperFactor = 0.7, extrudeSpeed = 120, dwellMs = 2000, extrusionMultiplier = 1.3, retractMm = 4.0, postRetractDwellMs = 2000, baseExtraMm = 0.3, baseDwellMs = 1000, dragSpeed = 600})`

A `blobDot`-family dome that **leans** in a chosen compass direction —
a raked / combed-looking tactile bump. **Separate from `blobDot`** (the
v17 hardware-confirmed default, which this does not touch). Reuses
`blobDot`'s volume model, with two `azimuthDeg`-driven changes:

1. **Sheared build** — the nozzle travels **`radius`** (= diameter/2) in
   the azimuth direction as it rises through `buildSteps` to the dome
   top, while extruding, so the apex ends up leaning at
   `(cx + radius·cos(az), cy + radius·sin(az), domeTop)`.
2. **Squish-then-drag (v3)** — after build → dwell → retract → dwell, the
   nozzle (still at the leaning apex) does **two straight no-extrusion
   moves**: (a) straight **down in Z** to bed level (`baseZ`), squishing
   the leaning blob onto the bed; then (b) a **lateral drag −azimuth**
   (against the lean) by **`diameter`** in XY, ending at the trailing
   edge of the base circle `(cx − radius·cos az, cy − radius·sin az)`.
   Drags the nozzle tip back across the whole blob to shape it (and sweep
   near any residual string, the job `blobDot`'s orbit does). *v2 did
   this as one diagonal move; v3 splits it Z-first then XY.*

Net sequence: build → dwell(`dwellMs`) → retract → dwell
(`postRetractDwellMs`) → squish down → lateral drag → next dot. **v2
removed the dome-height orbit + recenter** v1 had; **v3 split the drag**.

**Hardware status**: v1 verified by hand only, superseded by v2 before a
result came back; v2 likewise superseded by v3. **v3 printed and
confirmed working on real hardware** at `azimuthDeg` 0 (2mm + 3mm blobs,
`gap` = diameter,
`test_print_gcode/20260827-113000_dirblob-v3-testmode-squishdrag-gapEQdia-az0-2vs3mm.gcode`).
Default `diameter` was then set to 2.0 (user instruction). An
`azimuthDeg` 45 / 2mm test is generated
(`test_print_gcode/20260827-114728_dirblob-v3-testmode-az45-2mm-default.gcode`)
but **not yet printed** — nonzero azimuth is still hardware-unverified.

Same volume model as `blobDot`. Default is 2.0 (not `blobDot`'s 1.6) — set from the first hardware test |
| `azimuthDeg` | deg | 0 | Lean direction, CCW from +X (same convention as `hairyDot`). The build shears +azimuth; the lateral drag goes −azimuth. **Absolute here (single dot); in `freeformDirectionalBlobDotted` it is an offset from the path tangent** — see the Line section |
| `dragSpeed` | mm/min | 600 | Feedrate of both the squish-down and the lateral drag |

### Hairy dot — ✅ implemented, v11, v10 tentatively hardware-OK
`hairyDot(em, cx, cy, {rootDiameter = 2.0, baseZ = 0.2, buildSteps = 6, taperFactor = 0.7, extrudeSpeed = 120, baseExtraMm = 0.3, baseDwellMs = 1000, dwellMs = 2000, extrusionMultiplier = 1.3, hairThickness = null, hairLength = 10.0, pullExtrudeSpeed = 150, beadFlowMult = 3.5, dryRiseFeedDrop = 10, retractMm = 4.0, postRetractDwellMs = 500, hairDirection = "top", hairAzimuthDeg = null, hairElevationDeg = null, stringMm = 2.0, hairSpeed = 8000, clearanceZ = 0.5, clearanceSpeed = 600, overtravelMm = 2.0, overtravelSpeed = 600})`

A single dot with ONE hair strand pulled from its center — closes the
gap this section used to flag. Two parts: a ROOT DOME, built by
literally reusing `emitBlobDot`'s own tapered-rise mechanism and volume
model for a dot of `rootDiameter` (so "what a real 2mm `blobDot`
deposits" IS the root, not a custom approximation of it) — then a hair
pulled from that dome's own melt. Originally adapted the **Two-Step
Suspend Printing** mechanism from Wang et al., *"X-Hair: 3D Printing
Hair-like Structures with Multi-form, Multi-property and
Multi-function"* (UIST '24, https://doi.org/10.1145/3654777.3676360);
v6 departs from their mechanism in one deliberate way based on TPU
hardware testing — see below and `troubleshooting.md` §12 for the full
design history.

**Mechanism (v6, split in v10) — `hairLength` IS the extrude distance**:
1. **Extrude** — lays a real bead as the nozzle rises/travels away from
   the dome top. `hairThickness` sets the bead cross-section (via the
   shared `eRate()` helper); **(v8/v9)** its E is additionally scaled by
   `beadFlowMult` (default **3.5**) — an extra flow multiplier on this
   step only, on top of `extrusionMultiplier`, so the bead lays down more
   material and the hair comes out stiffer. **(v10)** this step is now
   split in two:
   - **1a. extrude-while-rising** — rise by exactly `eA` mm (numerically
     the filament amount) while extruding `eA`, so the Z feedrate and the
     *actual filament feedrate* are both `pullExtrudeSpeed` (default
     **150mm/min**, v10 — was 500/1000). In a `G1 Z.. E.. F..` move F is
     the Z rate and E is slaved to it; equal Z-distance and E-amount make
     the two rates equal.
   - **1b. dry rise** — finish the climb to the full `hairLength` height
     with NO extrusion, `dryRiseFeedDrop` mm/min slower (default 10, so
     140mm/min), so the bead is fully laid down before the tip is
     stretched up. (Skipped if `eA ≥ hairLength` — then 1a is the whole
     step and the rates can't be matched.)
2. **Retract** (`retractMm`) — fires immediately after the dry rise (the
   v5 fix, unchanged), then a `postRetractDwellMs` dwell.
3. **String** — a short, separate FAST zero-extrusion pull, `stringMm`,
   at `hairSpeed`. This is X-Hair's own "Stringing" step, kept as a
   finishing touch rather than the main length-definer (see below for
   why).
4. **Overtravel** (`overtravelMm`, this function's own addition, not
   part of X-Hair's process) — extends further past the string segment,
   same direction, still no extrusion, so the strand's actual tip stays
   clear of wherever the next dot happens to be.

**(v11) Direction is now a full polar vector.** All of steps 1–4 run
along one straight 3D line from the dome top, set by `hairElevationDeg`
(from the bed plane: 0 = flat, 90 = straight up) and `hairAzimuthDeg`
(CCW from +X). `hairDirection` is a shortcut string for the four cardinal
cases (`"top"` = el 90 — **still the default**; `"right"`/`"left"`/
`"bottom"` = el 0 at az 0/180/270). An explicit angle (either one)
overrides the string. The `clearanceZ` hop (step 2→3) now fires only for
near-horizontal pulls (`hairElevationDeg` < 30). An angled hair has real
XY reach — `(hairLength + stringMm + overtravelMm)·cos(elevation)` in the
azimuth direction — so the `verifyLayout` region for the texture must
include it.

**v7 — thickness follows length; base diameter is a feel knob**: two
independent "feel" observations from hardware drove this:
- **A longer strand flops more at a thickness that held a short one.**
  So `hairThickness` now defaults to `null`, meaning *derive it from
  `hairLength`*: `0.5 · (hairLength / 4.0)`, clamped to 0.4–2.0mm —
  anchored at the one known-good point (≈0.5mm held a 4–5mm hair). Pass a
  number to override. At `hairLength = 5` this gives 0.625mm; at 10, it
  gives 1.25mm.
- **`rootDiameter` changes how soft/tough the hair feels** — a smaller
  base prints a softer hair, a bigger base a tougher one. It stays a
  plain explicit parameter (not "fixed for now") and is deliberately
  **kept out of the thickness derivation**, so base-size and
  strand-thickness stay independently tunable while both are still being
  characterised.

**v8/v9 — thicker (and slower) bead by default**: the step-1 (Extrude)
bead was still laying too little material and the hair flopped, so
`beadFlowMult` multiplies that bead's E on top of `extrusionMultiplier`
— **only** the extruded bead, never the root dome. v8 shipped it at 2.0;
**v9 raised it to 3.5** (effective bead flow `extrusionMultiplier ·
beadFlowMult` = 1.3 · 3.5 = 4.55× the geometric `eRate`) and dropped
`pullExtrudeSpeed` 1000 → 500mm/min. Dial `beadFlowMult` toward 1.0 if
the hair comes out too fat/blobby.

**v10 — matched feedrate, then a dry rise**: the key requirement is that
during extrusion the **Z-up speed ≈ the filament feed speed**. A single
`G1 Z.. E.. F..` move can't guarantee that (F is the Z rate, E is
whatever it takes to finish together), so the Extrude step is split: sub
1a rises Z by *exactly* `eA` mm (the filament amount) while extruding
`eA`, which makes both rates equal `pullExtrudeSpeed` (dropped to
**150mm/min** in v10); sub 1b then finishes the climb to `hairLength`
height with no extrusion, `dryRiseFeedDrop` (10) mm/min slower — so the
bead is fully deposited *before* the tip is stretched up. If
`eA ≥ hairLength` the rates can't be matched while still reaching height;
1a becomes the whole step and 1b is skipped.

**Why v6 departs from X-Hair's own ratio-driven design**: X-Hair's paper
(PLA) has the STRING segment define most of the perceived hair
length/fineness, with EXTRUDE just a short lead-in (their "Extrusion
Length Ratio" α = extrude/total). **On real TPU hardware, the opposite
was observed**: "the extrude segment actually is more efficient in
defining the hair length... for TPU, somehow it seems that the string
from the stringing becomes very soft and can be ignored from the hairy
texture." So v6 makes the EXTRUDE segment directly equal to the target
hair length, and demotes the STRING segment to a small, independent
`stringMm` finishing pull. `retractMm` was also raised from the shared
global default (1.3mm) to 4.0mm, matching `blobDot`'s dot-specific
override — `RETRACT_SPEED` (900mm/min, already slowed from 1500
specifically to avoid TPU drive-gear damage — see `troubleshooting.md`
§1) is unaffected by this; retract amount and retract speed are
independent knobs.

**v5 fix retained**: the retract still fires immediately after the
extrude segment, not at the end of the pull — v4 followed X-Hair's own
step order literally (retract after Stringing) and was confirmed on
hardware to string across the entire pull, because this function's root
is a `blobDot`-style dome build that stores real residual melt pressure
(see `troubleshooting.md` §10's v10 diagnosis). v6 keeps v5's fix.

|---|---|---|---|
| `rootDiameter` | mm | 2.0 | Diameter of the root dome — built exactly like a `blobDot` of this diameter. **(v7)** Also a perceived-feel knob: smaller base → softer hair, bigger base → tougher hair. Not folded into the `hairThickness` derivation on purpose |
| `baseZ` | mm | 0.2 | Nozzle standoff for the root build, matches `blobDot`'s own default |

PER dot — see `troubleshooting.md` §1 (TPU filament damage) before using
a dense `gap` in `freeformHairyDotted` over a long path.

**Do NOT improvise** a single hairy dot by calling `freeformHairy` with
a zero-length path — that function's strand-placement logic assumes a
path with real extent and was never validated for a degenerate
zero-length case; use `hairyDot` instead, now that it exists.

For a line of hairy dots at regular spacing, use `freeformHairyDotted`
(see Line section below) rather than calling `hairyDot` in a loop.

**Hardware status**: v1 through v3 were never print-tested. **v4 WAS
printed and confirmed to still string across the entire pull** — the
retract-at-the-very-end timing (matching X-Hair's own literal step
order) wasn't enough given this function's pressurized `blobDot`-style
root. **v5 WAS printed and was a partial improvement**: "it is kind of
working" — moving the retract to right after the extrude segment
reduced the whole-pull stringing v4 showed, but the visible hair length
was observed to track the extrude segment rather than the full pull
distance. **v6 WAS printed**: the extrude segment defining
hair length worked, but at the fixed 0.5mm thickness a 4–5mm hair held
up while a 10mm one flopped a lot more, and the base diameter was noted
to change how soft/tough the hair feels. **v7** derived
`hairThickness` from `hairLength`; **v8** added `beadFlowMult` (2.0);
**v9** raised it to 3.5 and lowered `pullExtrudeSpeed` to 500 — v7–v9
were all test-mode prints, **none printed** before being superseded.
**v10** split the Extrude step so the along-path speed matches the
filament feed speed (both `pullExtrudeSpeed`, now 150) during deposition,
then a `dryRiseFeedDrop`-slower no-extrusion move finishes the length.
**v10 WAS printed** — user: **"I think it is working"** (tentative-
positive; not a firm confirmation). A follow-up (file `…-thick0p8-clamped…`)
doubled `hairThickness` to 0.8mm with the split clamping to `hairLength`
(per the user's choice); not yet printed.

**v11 (current)** generalises the pull direction to a polar vector
(`hairAzimuthDeg` / `hairElevationDeg`) — the two pre-v11 branches (pure
Z / pure XY) collapse into one, with the cardinal presets' G-code
unchanged; `"top"` (elevation 90) stays the default. Also adds
`stampOrder` to `freeformHairyDotted`. **Not yet print-tested.** Its
file
(`test_print_gcode/20260827-105639_hairy-dot-v11-testmode-polar-az30-el45-1vs2mm-len3.gcode`)
pulls at azimuth 30° / elevation 45° (same `hairLength` 3, `hairThickness`
0.8, `gap` 3, 1mm vs 2mm base as the last print) and, via `stampOrder:
"auto"`, stamps the line high-x → low-x so each strand trails behind its
dot. See `troubleshooting.md` §12 for the full design record across all
eleven versions.

## Line

All six styles share the mechanism in `texture_functions.js` §2
(`samplePath`), and all accept `xFunc, yFunc, tStart, tEnd`. **Every one
can follow any curve** — pass `t => 20+t, t => 100.0` for a horizontal
line, or any other `(x(t), y(t))` pair for an angle, arc, or custom curve.

**Safety**: `samplePath()` throws `PathTooSteepError` when a curve has a
direction change too sharp to print smoothly even after refining. This
means the SHAPE is unprintable (e.g. amplitude exceeding wavelength), not
that sampling needs tightening. Do not catch and retry — adjust the
shape's parameters. See `troubleshooting.md` §5.

### Solid line — ✅ implemented
`freeformSolid(em, xFunc, yFunc, tStart, tEnd, {width = 0.5, nLayers = 2, speed = 400, step = 0.1})`

| Parameter | Unit | Default | Spec equivalent |
|---|---|---|---|
| `tEnd - tStart` | mm | — | Total Length (when path is arc-length parameterized) |
| `width` | mm | 0.5 | Width |
| `nLayers` | count | 2 | Height (`nLayers` × 0.2mm) |

### Dashed line — ✅ implemented
`freeformDashed(em, xFunc, yFunc, tStart, tEnd, {segLen, gapLen, width = 0.5, nLayers = 2, speed = 400, step = 0.1})`

`segLen` and `gapLen` are **required** (no defaults) and throw a
`TypeError` if omitted or non-numeric. Both are measured along the path's
actual arc length, not the raw `t` parameter — this matters for
non-uniform-speed curves.

### Dotted line — ✅ implemented
`freeformDotted(em, xFunc, yFunc, tStart, tEnd, {gap = 10.0, dotRadius = 0.8, nLayers = 2, speed = 250, step = 0.1})`

Dots stamped at regular arc-length intervals (`gap`) along the path.

### Blob-dotted line — ✅ implemented, DEFAULT dotted-line style
`freeformBlobDotted(em, xFunc, yFunc, tStart, tEnd, {gap = 10.0, diameter = 1.6, baseZ = 0.2, buildSteps = 6, taperFactor = 0.7, extrudeSpeed = 120, dwellMs = 2000, extrusionMultiplier = 1.3, retractMm = 4.0, postRetractDwellMs = 2000, baseExtraMm = 0.3, baseDwellMs = 1000, orbitRadius = null, orbitPts = 16, orbitSpeed = 600, orbitLoops = 3, orbitDwellMs = 2000, blobClearanceMm = 0.3, liftZ = 5.0, liftSpeed = 600, liftDwellMs = 1000, topOrbitLoops = 3, step = 0.1})`

`blobDot()`-mechanism dots (point extrusion, no spiral fill) stamped at
regular arc-length intervals (`gap`) along the path. Preferred over
`freeformDotted` unless a flat, spiral-filled disc shape is specifically
needed. See the Blob dot entry under Dots above for parameter details.

### Directional blob-dotted line — ✅ implemented, tracks Directional blob dot (v3)
`freeformDirectionalBlobDotted(em, xFunc, yFunc, tStart, tEnd, {gap = null, diameter = 2.0, azimuthDeg = 0, baseZ = 0.2, buildSteps = 6, taperFactor = 0.7, extrudeSpeed = 120, dwellMs = 2000, extrusionMultiplier = 1.3, retractMm = 4.0, postRetractDwellMs = 2000, baseExtraMm = 0.3, baseDwellMs = 1000, dragSpeed = 600, stampOrder = "auto", step = 0.1})`

`directionalBlobDot()`-mechanism dots (a `blobDot` dome sheared so it
leans, plus a post-retract squish-then-drag shaping move) stamped at
regular arc-length intervals along the path. Like `freeformBlobDotted`
but directional; **separate from it** — the v17-confirmed blob dot is not
touched. See the Directional blob dot entry under Dots above for the
single-dot mechanism and parameters.

**Lean follows the path tangent.** Each dot leans along the direction the
line is travelling *at that dot's position*, so a curved line gives blobs
that each lean a different way (all raking "downstream"). This is
different from the single-dot `directionalBlobDot()`, where `azimuthDeg`
is an absolute compass heading — a lone dot has no path to follow.

**`azimuthDeg`** (default `0`): here it is an **offset** added to the
local tangent heading, degrees CCW. `0` = lean exactly along the
direction of travel; `90` = lean to the left of it; `180` = lean
backward. Per-dot azimuth is sampled from points a short distance either
side of the stop (`min(gap/2, 1mm)`), so curvature resolves per dot.

**`gap`** defaults to `null`, which resolves to `diameter` — dot spacing
equals blob diameter unless overridden.

**`stampOrder`** (`"auto"` | `"forward"` | `"reverse"`, default
`"auto"`): like `freeformHairyDotted`'s — if the (offset) lean at the
path start points forward along the path, the line is stamped in reverse
so each apex leans back over already-placed (cooled) dots rather than
toward the fresh next one. With the default offset `0` the lean always
points forward, so `"auto"` always reverses.

Straight-line output is unchanged by the tangent-following rule: on a
line heading +X the tangent is 0°, so `azimuthDeg` still reads as an
absolute heading there (the az-0 and az-45 hardware tests regenerate
byte-identical).

### Segmented line — ✅ implemented, v2 (independent thin/fat length + width), not yet print-tested
`freeformSegmented(em, xFunc, yFunc, tStart, tEnd, {thinLen = 8.0, thinWidth = 0.8, fatLen = 4.0, fatWidth = 1.6, z = 0.2, speed = 400, flowMult = 1.0, eprime = 1.6, primedwellS = 1.0, retractMm = 4.0, retractSpeed = 1000, step = 0.1})`

**(v2)** A continuous single-layer line that alternates between two
segment types, each with its **own length and its own bead width**:
`thinWidth × thinLen`, then `fatWidth × fatLen`, repeating to the end of
the path. This is the "independently-controlled length/width per segment
type" the original spec asked for — v1 had only one shared `segLen` and a
flow-rate `multiplier`.

v1 also **retracted `retractMm` between every segment with no matching
un-retract**, so each segment's own extrusion first had to refill that
4mm before any pressure reached the nozzle — printing every segment as a
**cone** (starved point at the start, full flow only near the end),
confirmed on hardware. v2 removes the inter-segment retract entirely: the
line is continuous, there is no travel move between segments, and the
retract was the direct cause. Just one prime at the start and one retract
at the very end. See `troubleshooting.md` §14.

| Parameter | Unit | Default | Notes |
|---|---|---|---|
| `thinLen` / `fatLen` | mm | 8.0 / 4.0 | Independent length of each segment type |
| `thinWidth` / `fatWidth` | mm | 0.8 / 1.6 | Bead width (in-plane "thickness") of each type. E per segment = `eRate(width, LAYER_HEIGHT) · segLen` — the standard bead model, same as `freeformSolid` |
| `z` | mm | 0.2 | Single layer. "Thickness" is width, NOT height — a taller fat segment would need a per-type layer count, not built |
| `speed` | mm/min | 400 | Feedrate for all segment moves |
| `flowMult` | — | 1.0 | Scales all segment E if the printed widths come out off |
| `eprime` / `primedwellS` | mm / s | 1.6 / 1.0 | One-time start prime after `goto()` leaves the nozzle retracted. Dropped from v1's 4.0 (which blobbed against v2's much smaller per-segment E) to just over the `RETRACT_MM` (1.3mm) the goto pulled |
| `retractMm` / `retractSpeed` | mm / mm·min⁻¹ | 4.0 / 1000 | The single final retract only. Distance/speed still the hardware-validated values, not the 1.3mm/900 global |

**Mechanism**: still uses `G91`/`G90` for the XY segment walk (the one
part of v1 that was hardware-validated). E is relative (`M83`, file-wide).
See `troubleshooting.md` §14 for the v1→v2 cone diagnosis and §4 for the
G91 note.

### Variable thickness line — ✅ implemented
`freeformVariableThickness(em, xFunc, yFunc, tStart, tEnd, {hMin = 0.16, hMax = 0.9, wavelength = 8.0, beadWidth = 0.8, zGap = 0.25, speed = 25, peakDwellMs = 300, step = 0.1})`

| Parameter | Unit | Default | Spec equivalent |
|---|---|---|---|
| `hMin` | mm | 0.16 | Min_extrusion (as bead height) |
| `hMax` | mm | 0.9 | Max_extrusion |
| `wavelength` | mm | 8.0 | Wavelength / length of one cycle |

`hMax`/`zGap` are user-validated as producing a non-flat result — see the
change log in `global_printing_parameters.md` before lowering `zGap`
below 0.25mm.

**No step-count parameter** — the spec asked for a discrete number of
steps; this uses a continuous sine profile sampled at a fixed `step` (mm)
instead. A genuinely stepped (staircase) profile would be a different
function, not built.

### Hairy line — ✅ implemented, vertical only
`freeformHairy(em, xFunc, yFunc, tStart, tEnd, {spacing = 5.0, esegmentMm = 1.2, retractMm = 1.3, dwellMs = 400, smallLift = 0.2, bigLift = 4.0, baseZ = 0.3, speed = 200, step = 0.1})`

Hair is pulled **vertically only** (straight up in Z). There is no
horizontal-draw option; a horizontal mechanism was explored earlier in
this project and abandoned in favor of this one.

**Retraction caution**: one retract/unretract cycle PER strand — the
highest cycle count of any function here. Read `troubleshooting.md` §1
before using dense `spacing` over a long path, and consider flagging the
cycle count to the user proactively.

### Hairy-dotted line — ✅ implemented, tracks Hairy dot (v11)
`freeformHairyDotted(em, xFunc, yFunc, tStart, tEnd, {gap = 10.0, rootDiameter = 2.0, baseZ = 0.2, buildSteps = 6, taperFactor = 0.7, extrudeSpeed = 120, baseExtraMm = 0.3, baseDwellMs = 1000, dwellMs = 2000, extrusionMultiplier = 1.3, hairThickness = null, hairLength = 10.0, pullExtrudeSpeed = 150, beadFlowMult = 3.5, dryRiseFeedDrop = 10, retractMm = 4.0, postRetractDwellMs = 500, hairDirection = "top", hairAzimuthDeg = null, hairElevationDeg = null, stringMm = 2.0, hairSpeed = 8000, clearanceZ = 0.5, clearanceSpeed = 600, overtravelMm = 2.0, overtravelSpeed = 600, stampOrder = "auto", step = 0.1})`

`hairyDot()`-mechanism dots (anchor + one pulled strand, with
independent thickness/length/direction/overtravel control) stamped at
regular arc-length intervals (`gap`) along the path. A different
mechanism from `freeformHairy` above (which is a simpler point-stamp
meant for dense strand spacing) — this one is the line-form of the
single "hairy dot".

**`stampOrder`** (**v11**, `"auto"` | `"forward"` | `"reverse"`, default
`"auto"`): `"auto"` projects the hair's azimuth onto the path's forward
tangent — if the strand leans *toward* the next dot, the whole line is
stamped in reverse so every strand ends up trailing *behind* its dot,
away from where the nozzle travels next. A vertical hair (no XY
component) leaves the order forward. `"forward"` / `"reverse"` force it.

**CAUTION**: same one retract/unretract cycle PER dot as `freeformHairy`
— see `troubleshooting.md` §1 before using a dense `gap`.

## Fill-in Texture

All fills take `region = {x0, y0, w, h}` — an axis-aligned rectangle.
**No other region shape is implemented.** Polygon and circle regions were
designed but not built; do not assume `region` accepts anything else.

### Outline only — ⚠️ no dedicated function
Draw the region's four edges as a closed `freeformSolid` path. No
`rectOutline` equivalent currently exists — a small gap worth closing if
this is used often.

### Solid fill — ✅ implemented
`fill(em, region, freeformSolid, {angleDeg: 0, gap: 0.45, width: 0.5, speed: 400})`

A small `gap` (≈ bead width, e.g. 0.45mm) makes adjacent passes fuse into
a solid sheet. **Ironing is NOT implemented** — known gap.

### Line shade fill — ✅ implemented, any angle
`fill(em, region, freeformSolid, {angleDeg: <any>, gap: 4.0, width: 0.5, speed: 400})`

Exact clipping at any angle (Liang-Barsky, via `clipLineToRect` /
`regionFillLines`) — not limited to 0°/45°.

**Verified**: swapping `freeformSolid` for `freeformDashed` genuinely
works and produces a dashed line-shade fill with no new code:
`fill(em, region, freeformDashed, {angleDeg: 0, gap: 4, segLen: 8, gapLen: 4})`.
(This combination was silently broken until the signature fix documented
in `troubleshooting.md` §8; it is now confirmed working — 2,630 real print
moves where there were previously zero.)

### Dots fill — ✅ implemented
`fill(em, region, freeformDotted, {angleDeg: 0, gap: <row spacing>, dotRadius: 0.7})`

A dots fill is the dotted-line primitive repeated at row intervals — same
generic mechanism, no separate implementation.

**Arrangement**: rectangular grid only (implicit in how `fillRegion` lays
out parallel lines). Hexagonal and random arrangements are not implemented.

### Hairy fill — ✅ implemented
`fill(em, region, freeformHairy, {angleDeg: 0, gap: <row spacing>, spacing: <strand spacing>})`

**Highest retraction-cycle-count texture in the library** — one retract
per strand × (rows × strands per row). Read `troubleshooting.md` §1 before
combining dense `spacing` and `gap` over a large region.

### Diamond / checkerboard fill — ✅ implemented, ⚠️ SPECIAL CASE
`fill(em, region, DIAMOND, {diag: 8.0, fillGap: 0.6})`
→ routes to `diamondFillRegion(em, region, {diag, fillGap})`

| Parameter | Unit | Default |
|---|---|---|
| `diag` | mm (diamond diagonal, corner to corner) | 8.0 |
| `fillGap` | mm (scanline spacing inside filled diamonds) | 0.6 |

**This is NOT a `fillRegion` recipe and must never be reimplemented as
one.** The lattice's two crossing line families superficially resemble
"lines at a gap," but *which* diamonds get filled is a discrete
checkerboard-parity selection over a rotated grid — no `gap` value
produces that selection as a side effect.

It is also the most bug-prone algorithm in this project's history: **four
attempts** were needed to get the parity math right, and **three of those
four looked correct in a rendered preview and were not**.

**Mandatory verification**: after any diamond fill, call
`verifyCheckerboard(diamonds, diag)` on the returned value and confirm
`violations === 0` before treating the output as correct. Visual
inspection is not sufficient evidence for this pattern — see
`troubleshooting.md` §3.

Note: `angleDeg` and `gap` passed to a `DIAMOND` fill are silently
ignored (verified harmless — the checkerboard still verifies clean), but
omit them for clarity.
